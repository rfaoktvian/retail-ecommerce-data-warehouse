# Naming Conventions

This document defines the naming conventions for schemas, tables, views, columns, dbt models, and Airflow tasks used in the `retail-ecommerce-data-warehouse` project.

The goal of these conventions is to ensure consistency, readability, maintainability, and clear data lineage across the entire data warehouse.

# General Principles

Follow these principles for all database objects.

- Use **snake_case**.
- Use only lowercase letters.
- Separate words using underscores (`_`).
- Use English for all database objects, file names, and code.
- Comments and documentation may be written in Bahasa Indonesia.
- Avoid SQL reserved keywords such as `order`, `group`, and `table`.
- Prefer descriptive names over short abbreviations.
- Be consistent throughout the entire project.

# Table Naming Conventions

Each data warehouse layer has different naming rules.

# Bronze Layer

Bronze contains raw data extracted directly from source systems.

Table names must preserve the original business entity and always include the source system as a prefix.

Pattern

```
<source_system>_<entity>
```

Where

- `source_system` identifies where the data originated.
- `entity` is the original entity name from the source.

Allowed source systems

- `postgres`
- `csv`
- `json`

Examples

| Table | Description |
|--------|-------------|
| `postgres_orders` | Raw orders extracted from PostgreSQL |
| `postgres_order_items` | Raw order items |
| `csv_sellers` | Raw sellers CSV |
| `csv_geolocation` | Raw geolocation CSV |
| `json_reviews` | Raw reviews extracted from JSON |

All Bronze tables are stored in the **bronze** dataset.

Example

```
retail-dwh-project.bronze.postgres_orders
```

---

# Silver Layer

Silver contains cleaned, standardized, validated, and deduplicated data.

The table name remains exactly the same as its Bronze counterpart to preserve clear lineage.

Pattern

```
<source_system>_<entity>
```

Examples

| Bronze | Silver |
|---------|---------|
| `postgres_orders` | `postgres_orders` |
| `csv_sellers` | `csv_sellers` |
| `json_reviews` | `json_reviews` |

Typical transformations include

- Data type casting
- Null handling
- Standardizing values
- Removing duplicates
- Parsing JSON
- Basic validation

All Silver tables are stored in the **silver** dataset.

Example

```
retail-dwh-project.silver.postgres_orders
```

Keeping the same table name between Bronze and Silver makes data lineage easy to understand and trace.

---

# Gold Layer

Gold contains business-ready data models designed for analytics, reporting, and dashboards.

Unlike Bronze and Silver, Gold tables no longer include the source system in their names.

Pattern

```
<category>_<entity>
```

Where

- `category` describes the table type.
- `entity` is a business-friendly name.

Allowed categories

- `dim`
- `fact`
- `report`

Examples

| Table | Description |
|--------|-------------|
| `dim_customers` | Customer dimension |
| `dim_products` | Product dimension |
| `dim_sellers` | Seller dimension |
| `dim_date` | Date dimension |
| `dim_geography` | Geography dimension |
| `fact_sales` | Sales fact table |
| `fact_payments` | Payment fact table |
| `fact_reviews` | Review fact table |
| `report_monthly_sales` | Monthly aggregated sales report |

All Gold tables are stored in the **gold** dataset.

Example

```
retail-dwh-project.gold.fact_sales
```

Category reference

| Prefix | Purpose |
|---------|---------|
| `dim_` | Dimension table |
| `fact_` | Fact table |
| `report_` | Pre-aggregated reporting table |

# Column Naming Conventions

# Surrogate Keys

Every dimension table in the Gold layer uses surrogate keys.

Pattern

```
<entity>_key
```

Examples

| Column |
|---------|
| `customer_key` |
| `product_key` |
| `seller_key` |
| `date_key` |

These keys are generated by dbt, for example using `dbt_utils.generate_surrogate_key()`.

The original source IDs are retained as natural keys for traceability.

Examples

- `customer_id`
- `product_id`
- `seller_id`

---

# Technical Columns

Metadata columns generated by the pipeline must use the `dwh_` prefix.

Pattern

```
dwh_<column_name>
```

Examples

| Column | Description |
|---------|-------------|
| `dwh_load_date` | Timestamp when the record was loaded |
| `dwh_source_system` | Original data source |
| `dwh_batch_id` | Pipeline batch identifier |

The `dwh_` prefix is reserved exclusively for technical metadata and must never be used for business attributes.

---

# dbt Model Naming

This project uses **dbt** to perform transformations.

Each model filename must exactly match the final table or view name produced by dbt.

Examples

| File | Output |
|------|--------|
| `models/silver/postgres_orders.sql` | `silver.postgres_orders` |
| `models/gold/fact_sales.sql` | `gold.fact_sales` |

Intermediate staging models should use the `stg_` prefix.

Example

```
stg_postgres_orders.sql
```

# Airflow Task Naming

Airflow task IDs follow the pattern

```
<action>_<target>
```

Examples

| Task ID | Description |
|----------|-------------|
| `extract_postgres` | Extract PostgreSQL data |
| `extract_csv` | Extract CSV data |
| `extract_json` | Extract JSON data |
| `load_bronze` | Load data into Bronze |
| `transform_silver` | Build Silver models |
| `test_silver` | Execute Silver data tests |
| `transform_gold` | Build Gold models |
| `test_gold` | Execute Gold data tests |

Typical pipeline order

```
extract_postgres
extract_csv
extract_json
load_bronze
transform_silver
test_silver
transform_gold
test_gold
```

| Layer | Naming Pattern | Example |

# Summary

The project follows a simple naming strategy across all layers.

- Bronze preserves the original source naming.
- Silver keeps the same naming while improving data quality.
- Gold uses business-friendly names for analytics.
- Surrogate keys always end with `_key`.
- Technical metadata always begins with `dwh_`.
- dbt model filenames match the final table names.
- Airflow tasks follow the `<action>_<target>` convention.

Following these conventions ensures consistency, improves readability, and makes data lineage easier to understand throughout the project.
